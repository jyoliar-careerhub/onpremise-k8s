# 작업 일지 - 2026-02-18 14:57

## 작업 내용: Tailscale VPN 통합 방안 조사/검토

### 배경

자택 LAN(10.18.x.x)에 있는 K8s 클러스터에 외부에서 접근하고, 향후 AWS EC2 워커 노드를 추가할 수 있도록 Tailscale VPN 도입을 검토.

### 검토 과정 (4단계)

#### 1단계: 노드마다 Tailscale 설치 방안 검토

모든 K8s 노드에 Tailscale을 설치하여 100.x.x.x IP로 K8s를 구축하는 방안 조사.

- `ansible_host`를 참조하는 위치 8곳 식별 (etcd, kubeadm, kube-vip, haproxy, keepalived, smoke-test)
- Tailscale은 L3 터널이므로 ARP 불가 → kube-vip ARP 모드 사용 불가
- kubelet `--node-ip`, Flannel `--iface=tailscale0` 추가 필요
- **치킨-에그 문제 발견**: Ansible이 LAN IP로 SSH 접속해야 하는데, Tailscale IP를 K8s에 사용하려면 `ansible_host` 분리 필요

#### 2단계: 워크플로우 분리 방안 검토

VPN 설정 워크플로우 + K8s 구축 워크플로우로 분리하는 방안.

- host_vars를 인터페이스로 사용 (`k8s_ip | default(ansible_host)` 패턴)
- 템플릿 8곳 수정 필요
- kube-vip 대체: Control Plane HA(로컬 HAProxy) + Service LB(Tailscale Operator 또는 NodePort)

#### 3단계: kube-vip 이중 기능 인식

kube-vip가 담당하는 두 기능(Control Plane HA + Service type: LoadBalancer) 모두 대체 필요.

- MetalLB L2/BGP 모두 Tailscale에서 불가
- 권장 조합: 로컬 HAProxy(CP HA) + Tailscale K8s Operator(Service LB)

#### 4단계: Subnet Router 방안 발견 (최종 채택)

AWS Client VPN과의 비교 분석에서 착안. 핵심 질문: "노드에 IP를 2개 만들지 않는 방법은?"

- **Subnet Router**: 각 사이트의 게이트웨이 장치에만 Tailscale 설치
- K8s 노드에는 Tailscale 미설치 → IP 1개, 기존 LAN IP 그대로
- 사이트 간 라우팅만 Subnet Router가 처리
- AWS Client VPN과 유사하지만 **양방향 + 멀티사이트** 가능

### 최종 결론: Subnet Router 방식 권장

| 평가 항목 | 노드마다 Tailscale | Subnet Router |
|-----------|:-:|:-:|
| K8s 템플릿 수정 | 8곳 | **0곳** |
| 노드 IP 개수 | 2개 | **1개** |
| 치킨-에그 문제 | 있음 | **없음** |
| kube-vip 사용 | 불가 | **가능** (마스터 같은 사이트) |
| 워크플로우 변경 | 필요 | **불필요** |
| 추가 인프라 | 없음 | SR 장치 (공유기 또는 Pi) |

**핵심 가치**: Tailscale을 K8s 위가 아닌 K8s 아래(인프라 레이어)에 배치하여, K8s에 대해 투명(transparent)하게 동작.

### 주요 기술 포인트

- **Subnet Router 설정**: `tailscale up --advertise-routes=CIDR --snat-subnet-routes=false`
- **커널 파라미터**: `net.ipv4.ip_forward=1`, `rp_filter=2` (loose)
- **AWS**: Source/Dest Check 비활성화 필수, VPC Route Table에 자택 서브넷 경로 추가
- **SNAT**: 비활성화 권장 (소스 IP 투명성). 양방향 라우팅 설정이 어차피 필요하므로 SNAT의 단순화 이점 없음
- **HA**: 동일 서브넷을 광고하는 복수 SR 배포 → Tailscale이 자동 failover (Free 플랜 포함)
- **성능**: 사이트 간 WireGuard 암호화 오버헤드는 노드마다 Tailscale과 동일. 사이트 내 통신은 평문(LAN 직접)으로 오히려 유리
- **ACL**: `autoApprovers`로 route 자동 승인 가능 → 수동 개입 최소화

### 구현 로드맵

- **Phase 1**: 자택 공유기에 Tailscale SR 설정 → 외부에서 K8s 접근 (K8s 프로젝트 변경 없음)
- **Phase 2**: AWS에 SR EC2 배포 → 워커 노드 추가 (인벤토리에 노드 추가만)
