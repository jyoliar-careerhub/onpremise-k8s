# 작업 일지 - 2026-07-31 16:08

## 작업 내용: kubeadm 커스텀 설정의 ClusterConfiguration 전환 (ops-workflow#27)

### 배경

k8s v1.34.9 패치 업그레이드(ops-workflow#25) 준비 중, 클러스터의 kubeadm 커스텀 설정이 ClusterConfiguration 선언(`kube-system/kubeadm-config` ConfigMap)이 아니라 **init 이후 static pod 매니페스트 직접 패치**로 적용되어 온 것을 확인했다. kubeadm은 CLI 도구라 이런 out-of-band 변경을 감지·역동기화하지 않으며, `kubeadm upgrade`가 ConfigMap 기준으로 매니페스트를 재생성하는 순간 커스텀 인자가 전부 원복된다. 업그레이드 전에 선언을 실제 상태와 일치시키고, kubeadm 명령으로 선언→매니페스트 실체화 동작을 검증한다.

### 1단계: 전수 대조 (2026-07-31, 읽기 전용 kubectl 실측)

마스터 3대(raspberrypi-0/1/2) × 4컴포넌트의 static pod 인자·볼륨과 `kubeadm-config`·`kubelet-config`·`kube-proxy` ConfigMap을 대조했다.

#### 이탈 (live 매니페스트에는 있으나 ClusterConfiguration 선언에 없음) — 4건

| # | 컴포넌트 | 인자 | 적용 경로 (out-of-band) | 원복 시 영향 |
|---|---|---|---|---|
| 1 | kube-apiserver | `--encryption-provider-config=/etc/kubernetes/pki/enc-config.yaml` | `encrypt-secrets` 롤 (lineinfile) | etcd에 암호화 저장된 Secret 복호화 불가 |
| 2 | kube-apiserver | `--service-account-issuer=https://k8s-oidc.jyo-liar.com` | `config-oidc-issuer` 롤 (lineinfile) | SA 토큰 발급자 변경 — 인증 파손 |
| 3 | kube-controller-manager · kube-scheduler | `--bind-address=0.0.0.0` (기본 127.0.0.1) | `config-kube-scheduler-and-controller` 롤 (replace) | Prometheus 수집 단절 |
| 4 | etcd | `--listen-metrics-urls=http://0.0.0.0:2381` (기본 127.0.0.1) | 2026-03-05 ansible ad-hoc 직접 수정 (19aec44 일지) | Prometheus etcd job 단절 |

#### 이탈 아님 (확인 완료)

- **마스터 간 일관성**: 4컴포넌트 인자가 3대 모두 동일 (차이는 노드별 IP·etcd `initial-cluster`의 join 이력뿐 — kubeadm의 정상 per-node 생성분).
- **볼륨 마운트**: 4컴포넌트 × 3대 전부 kubeadm 표준 볼륨만 존재 — `extraVolumes` 손패치 없음. `enc-config.yaml`은 표준 `k8s-certs`(/etc/kubernetes/pki) 마운트 아래 위치해 별도 볼륨이 불필요한 구조.
- **kubelet-config ConfigMap**: `serverTLSBootstrap: true`는 init 시점 KubeletConfiguration으로 선언되어 ConfigMap에 존재 — 선언 경로 정상.
- **kube-proxy ConfigMap**: `metricsBindAddress: "0.0.0.0:10249"`는 ConfigMap 자체에 반영되어 있음(2026-03-05 수동 수정). kubeadm upgrade는 기존 componentconfig ConfigMap을 읽어 보존하므로 원복 위험 없음. 단, 신규 구축 경로는 여전히 post-init 패치(`config-kube-proxy` 롤) 의존 — init 템플릿에 KubeProxyConfiguration 문서로 선언하는 개선 여지 있음.

#### 이탈의 근본 원인

init 템플릿(`kubeadm-init-prep/templates/kubeadm-config.yaml`)이 `apiVersion: kubeadm.k8s.io/v1beta4`를 선언하면서 extraArgs를 **v1beta3 map 표기**로 기술 — v1beta4의 extraArgs는 name/value 목록이라 map 표기는 반영되지 않았고, 결국 모든 커스텀이 post-init 매니페스트 패치로 흘러갔다.

### 2단계: 코드 수정 — 템플릿을 유일한 진실로

- **init 템플릿**: extraArgs를 v1beta4 name/value 목록으로 정정. `encryption-provider-config`는 `apiserver_encryption_enabled` 인벤토리 변수로 게이트(신규 init 시점에는 enc-config.yaml이 없어 무조건 켜면 apiserver 기동 실패). controllerManager/scheduler `bind-address: 0.0.0.0` 선언 추가. `InitConfiguration.localAPIEndpoint.advertiseAddress: {{ ansible_host }}`로 마스터별 IP 명시.
- **신규 playbook `kubeadm-reconfigure.yaml`**: 렌더링 → `kubeadm config validate` → 첫 마스터에서 `kubeadm init phase upload-config kubeadm`(defaulting은 kubeadm이 수행해 ConfigMap 기록) → 마스터 1대씩(serial: 1) 컴포넌트별 `kubeadm init phase control-plane <c>`/`etcd local` 재생성 → 컴포넌트별 헬스 대기(livez/healthz/2381 health) → 클러스터 응답 확인. `-e kubeadm_reconfigure_dry_run=true`로 무변경 미리보기 가능.
- **dry-run 함정 (kubeadm v1.34.0)**: phase 단독 `--dry-run`은 `--kubeconfig`를 무시하고 dry-run 디렉터리 안의 `admin.conf`만 찾는다. `KUBEADM_INIT_DRYRUN_DIR`로 디렉터리를 고정하고 admin.conf를 복사해 넣는 방식으로 우회했다. control-plane phase의 dry-run은 매니페스트를 stdout이 아니라 그 디렉터리에 파일로 쓴다(etcd phase만 stdout에 출력).
