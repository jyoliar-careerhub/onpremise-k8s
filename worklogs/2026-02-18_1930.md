# 작업 일지 - 2026-02-18 19:30

## 작업 내용: Public Endpoint 설계, Pi 5 공유기 검토, SR 아키텍처 문서화

### 배경

이전 세션에서 Tailscale Subnet Router 방식을 채택한 이후, 관련 후속 주제 3가지를 검토하고 문서화.

### 1. K8s Service Public Endpoint 노출 설계

K8s LoadBalancer 서비스를 인터넷에 공개하는 방안 검토.

**전제 조건 확인:**
- 노출 대상: HTTP/HTTPS 트래픽만 (L7)
- ISP 공인 IP 보유 (포트포워딩 가능)
- 도메인 보유, 단 Cloudflare DNS가 **아님**

**검토한 방안:**
| 방안 | 채택 여부 | 이유 |
|------|:-:|------|
| Cloudflare Tunnel | 제외 | DNS를 Cloudflare로 이전해야 함, 외부 의존도 높음 |
| **Ingress + cert-manager + 포트포워딩** | **채택** | DNS 이전 불필요, 기존 인프라 활용 |

**아키텍처:** 인터넷 → 공유기 :443 → kube-vip LB IP → Nginx Ingress → K8s Service

### 2. Raspberry Pi 5 커스텀 공유기 검토

공유기 설정(포트포워딩)도 IaC로 관리하려는 목적으로 Pi 5를 공유기로 개조하는 방안 검토.

**결론: 과잉 엔지니어링**
- 공유기에 필요한 설정은 포트포워딩 2줄(80, 443)과 멀티사이트 시 정적 라우트 1줄뿐
- Pi 5 풀 라우터는 PCIe HAT + NVMe + 냉각 필요 (~$100-130), SPOF 위험
- 기존 공유기 유지 + Pi 5는 SR 전용이 가장 안전하고 단순

### 3. SR 아키텍처 상세 문서화

"공유기 + SR 전용 Pi 5" 구조에 대한 상세 설명 문서 2건 작성.

#### 구조 설명 문서
- 물리적 토폴로지: Pi 5 SR은 LAN에 붙어있는 평범한 장치, 공유기와 K8s 사이에 끼어들지 않음
- 4가지 트래픽 시나리오별 동작 원리
- **문서 수정**: 공유기에 변경이 필요 없다는 초기 기술이 잘못됨을 발견
  - 단일 사이트 (외부 원격 접속만): 공유기 변경 불필요
  - 멀티사이트 (자택 + AWS): 정적 라우트 `10.0.0.0/16 → Pi 5 SR` 필요

#### 외부 접속 상세 과정 문서
- 카페 노트북 → K8s 마스터까지의 전체 패킷 흐름을 10단계로 분해
- 각 단계별 패킷 구조, IP 헤더, 암호화 과정 도식화
- NAT traversal (STUN/UDP hole punching), DERP 릴레이, WireGuard 패킷 구조 설명
- 응답 귀환 경로: SNAT 처리 방식과 conntrack 동작 설명
- 레이턴시 분석, 자주 하는 오해 정리

### 주요 발견 사항

- **공유기 정적 라우트 필요성**: K8s 노드는 Tailscale을 모르므로, AWS 대역 패킷을 기본 게이트웨이(공유기)로 보냄. 공유기가 이를 Pi 5 SR로 전달해야 함. 기존 문서 2건 수정 반영.
- **SR은 IP 할당과 무관**: SR은 DHCP와 무관하며, route 광고만 담당. IP 할당은 기존 공유기가 그대로 수행.
- **포트포워딩 불필요 이유**: Pi 5 SR이 먼저 outbound UDP 연결을 맺으므로, 외부 패킷은 NAT 매핑을 통해 자동 전달됨.
