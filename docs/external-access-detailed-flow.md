## 1단계: Tailscale 로그인 및 피어 정보 수신

노트북에서 Tailscale을 켜는 순간 일어나는 일.

```
MacBook                          Tailscale 조정 서버
  │                              (login.tailscale.com)
  │                                     │
  │  ① HTTPS 연결 (TCP 443)            │
  │  ─────────────────────────────────→ │
  │  "나는 100.64.0.1이고, 로그인했다"   │
  │                                     │
  │  ② 피어 목록 + route 정보 수신       │
  │  ←───────────────────────────────── │
  │  {                                  │
  │    peers: [                         │
  │      {                              │
  │        name: "pi5-sr",              │
  │        tailscale_ip: 100.64.0.2,    │
  │        public_key: "abc123...",      │
  │        endpoints: [                 │
  │          "203.0.113.50:41641",      │  ← Pi 5 SR의 공인 IP:포트
  │          "100.64.0.2:41641"         │  ← Tailscale IP
  │        ],                           │
  │        advertised_routes: [         │
  │          "10.18.0.0/16"             │  ← 자택 LAN 전체
  │        ]                            │
  │      }                              │
  │    ]                                │
  │  }                                  │
  │                                     │
  │  ③ 로컬 라우팅 테이블 업데이트       │
  │  10.18.0.0/16 → tailscale0         │
  │  (이 대역의 트래픽은 Tailscale로)    │
```

**핵심**: 조정 서버는 "10.18.0.0/16을 Pi 5 SR이 광고하고 있다"는 정보를 노트북에 전달한다. 노트북의 Tailscale 클라이언트는 이 정보를 바탕으로 **로컬 라우팅 테이블에 10.18.0.0/16 → tailscale0 인터페이스** 항목을 추가한다.

조정 서버가 전달하는 것은 **메타데이터**(공개키, 엔드포인트 주소, 광고 경로)뿐이다. 실제 데이터 트래픽은 조정 서버를 경유하지 않는다.

## 2단계: kubectl 명령 실행 → 패킷 생성

카페에서 `kubectl get nodes --kubeconfig .kube/baremetal.config`를 실행한다.

```
MacBook (사용자 공간)
  │
  │  kubectl이 kubeconfig 읽음
  │  server: https://10.18.1.1:6443
  │
  │  TCP 연결 시도: 10.18.1.1:6443
  │
  ▼
MacBook (커널, 라우팅 테이블 조회)
  │
  │  "10.18.1.1은 어디로 보내야 하나?"
  │
  │  라우팅 테이블:
  │  ┌──────────────────────────────────────────┐
  │  │ 목적지            게이트웨이    인터페이스  │
  │  │ 192.168.0.0/24   직접         en0 (Wi-Fi)│
  │  │ 10.18.0.0/16     직접         tailscale0 │ ← Tailscale이 추가한 항목
  │  │ 0.0.0.0/0        192.168.0.1  en0 (Wi-Fi)│
  │  └──────────────────────────────────────────┘
  │
  │  → 10.18.1.1은 10.18.0.0/16에 매칭 → tailscale0 인터페이스로 전달
  │
  ▼
Tailscale 클라이언트 (userspace)
  │
  │  tailscale0 인터페이스에서 패킷 수신
  │  원본 패킷:
  │  ┌─────────────────────────────────────┐
  │  │ IP Header                           │
  │  │   src: 100.64.0.1 (MacBook)        │
  │  │   dst: 10.18.1.1  (kube-vip VIP)   │
  │  │ TCP Header                          │
  │  │   dst_port: 6443                    │
  │  │ Payload: TLS ClientHello            │
  │  └─────────────────────────────────────┘
  │
  │  "10.18.1.1은 10.18.0.0/16 범위 → Pi 5 SR(100.64.0.2)로 보내야 한다"
```

**핵심**: kubectl은 Tailscale의 존재를 전혀 모른다. 일반적인 TCP 연결을 시도할 뿐이며, OS 라우팅 테이블이 해당 패킷을 tailscale0 인터페이스로 전달한다.

## 3단계: WireGuard 암호화 및 NAT 통과

Tailscale 클라이언트가 패킷을 WireGuard로 암호화하여 Pi 5 SR에게 전송한다.

### 3-A: 직접 연결 시도 (NAT Traversal)

```
MacBook Tailscale                Tailscale 조정 서버              Pi 5 SR Tailscale
  │                                     │                              │
  │  "Pi 5 SR의 endpoint는              │                              │
  │   203.0.113.50:41641"               │                              │
  │                                     │                              │
  │  ① STUN 요청 (내 공인 IP 확인)      │                              │
  │  ─────────────────────────────────→ │                              │
  │  "너의 공인 IP는 198.51.100.20"     │                              │
  │  ←───────────────────────────────── │                              │
  │                                     │                              │
  │  ② UDP hole punching 시도                                          │
  │  ─────────────────────────────────────────────────────────────────→│
  │  src: 198.51.100.20:12345                                          │
  │  dst: 203.0.113.50:41641                                           │
  │                                     │                              │
  │  ③ 상대도 동시에 hole punching                                     │
  │  ←─────────────────────────────────────────────────────────────────│
  │  src: 203.0.113.50:41641                                           │
  │  dst: 198.51.100.20:12345                                          │
  │                                     │                              │
  │  ④ 양방향 UDP 경로 성립 (direct connection)                         │
  │  ◄════════════════════════════════════════════════════════════════►│
```

**STUN(Session Traversal Utilities for NAT)**: 자신의 공인 IP와 포트를 알아내는 프로토콜. 카페 공유기 뒤에 있어도 STUN 서버를 통해 외부에서 보이는 IP:포트를 확인할 수 있다.

**UDP Hole Punching**: 양쪽이 거의 동시에 상대방에게 UDP 패킷을 보내면, 양쪽 NAT 장비 모두 "내가 보낸 패킷의 응답"이라고 판단하여 통과시킨다. 이 방식으로 양쪽 모두 NAT 뒤에 있어도 직접 연결이 가능하다.

### 3-B: 직접 연결 실패 시 (DERP Relay)

엄격한 NAT(Symmetric NAT) 등으로 직접 연결이 불가능한 경우, Tailscale의 DERP 릴레이 서버를 경유한다.

```
MacBook              DERP 서버               Pi 5 SR
  │                  (Tailscale 운영)          │
  │                  (예: Tokyo DERP)          │
  │                        │                   │
  │  HTTPS (TCP 443)       │   HTTPS (TCP 443) │
  │  ──────────────────→  │  ←──────────────── │
  │                        │                   │
  │  암호화된 패킷 전달     │                   │
  │  ──────────────────→  │ ──────────────────→│
  │                        │                   │
  │  응답 패킷 전달         │                   │
  │  ←──────────────────  │ ←──────────────────│
```

- DERP 서버는 **암호화된 패킷을 중계**할 뿐, 내용을 볼 수 없다 (E2E 암호화)
- TCP 443을 사용하므로 거의 모든 네트워크에서 통과 가능
- 직접 연결보다 레이턴시가 높으므로, Tailscale은 백그라운드에서 계속 직접 연결을 시도하며, 성공하면 자동으로 전환

### 3-C: WireGuard 암호화 패킷 구조

직접 연결이든 DERP 경유든, 실제 전송되는 패킷의 구조는 동일하다.

```
카페 공유기가 인터넷으로 내보내는 패킷:
┌───────────────────────────────────────────────────────┐
│ 외부 IP Header                                        │
│   src: 198.51.100.20 (카페 공유기의 공인 IP, NAT 후)   │
│   dst: 203.0.113.50  (자택 공유기의 공인 IP)           │
│                                                       │
│ UDP Header                                            │
│   src_port: 12345 (임의)                              │
│   dst_port: 41641 (WireGuard)                         │
│                                                       │
│ ┌───────────────────────────────────────────────────┐ │
│ │ WireGuard Header                                  │ │
│ │   type: 4 (transport data)                        │ │
│ │   receiver: 0x1a2b3c4d                            │ │
│ │   counter: 42                                     │ │
│ │                                                   │ │
│ │ ┌───────────────────────────────────────────────┐ │ │
│ │ │ 암호화된 원본 패킷 (ChaCha20-Poly1305)        │ │ │
│ │ │                                               │ │ │
│ │ │   IP Header                                   │ │ │
│ │ │     src: 100.64.0.1 (MacBook Tailscale IP)   │ │ │
│ │ │     dst: 10.18.1.1  (kube-vip VIP)           │ │ │
│ │ │   TCP Header                                  │ │ │
│ │ │     dst_port: 6443                            │ │ │
│ │ │   Payload: TLS ClientHello                    │ │ │
│ │ │                                               │ │ │
│ │ └───────────────────────────────────────────────┘ │ │
│ └───────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────┘

카페 공유기가 보는 것: 일반 UDP 패킷 (암호화된 내용은 알 수 없음)
자택 공유기가 보는 것: Pi 5가 인터넷에서 UDP 패킷을 수신 (일반적인 트래픽)
```

**핵심**: 카페 공유기와 자택 공유기 모두 이 트래픽을 **일반 UDP 통신**으로 인식한다. 특별한 포트포워딩이나 설정이 필요 없는 이유다.

## 4단계: 자택 공유기 통과 → Pi 5 SR 도착

```
인터넷
  │
  │  UDP 패킷 (dst: 203.0.113.50:41641)
  │
  ▼
자택 공유기 (203.0.113.50)
  │
  │  NAT 테이블 조회:
  │  "이 패킷은 Pi 5 SR(10.18.1.50)이 보낸 outbound UDP의 응답이다"
  │  (Pi 5 SR이 먼저 outbound 연결을 맺었으므로 NAT 테이블에 매핑이 있음)
  │
  │  dst 변환: 203.0.113.50:41641 → 10.18.1.50:41641
  │
  ▼
Pi 5 SR (10.18.1.50, eth0)
  │
  │  UDP 포트 41641에서 수신
  │  → Tailscale/WireGuard 데몬이 처리
```

**공유기에 포트포워딩이 필요 없는 이유**: Pi 5 SR이 먼저 조정 서버와 STUN 서버에 outbound UDP 연결을 맺는다. 공유기는 이 outbound 연결에 대한 NAT 매핑을 생성하고, 이후 외부에서 오는 UDP 응답을 자동으로 Pi 5에게 전달한다. 이것이 "NAT traversal"이다.

## 5단계: Pi 5 SR에서의 WireGuard 복호화 및 IP 포워딩

```
Pi 5 SR (Tailscale/WireGuard 데몬)
  │
  │  ① WireGuard 복호화
  │  ─────────────────────────
  │  암호화된 페이로드 → ChaCha20-Poly1305 복호화
  │  → 원본 IP 패킷 추출
  │
  │  복호화된 패킷:
  │  ┌─────────────────────────────────────┐
  │  │ IP Header                           │
  │  │   src: 100.64.0.1 (MacBook)        │
  │  │   dst: 10.18.1.1  (kube-vip VIP)   │
  │  │ TCP Header                          │
  │  │   dst_port: 6443                    │
  │  └─────────────────────────────────────┘
  │
  │  ② SNAT 적용 여부 판단
  │  ─────────────────────────
  │  --snat-subnet-routes=false 설정됨
  │  → src IP를 변환하지 않음
  │  → 원본 소스 IP(100.64.0.1) 유지
  │
  │  ③ IP 포워딩 (커널)
  │  ─────────────────────────
  │  net.ipv4.ip_forward = 1 이므로 다른 인터페이스로 전달 가능
  │
  │  커널 라우팅 테이블:
  │  ┌──────────────────────────────────────────┐
  │  │ 목적지            게이트웨이    인터페이스  │
  │  │ 10.18.1.0/24     직접         eth0       │
  │  │ 10.18.0.0/16     10.18.x.1    eth0       │
  │  │ 100.64.0.0/10    직접         tailscale0 │
  │  └──────────────────────────────────────────┘
  │
  │  → dst 10.18.1.1은 10.18.1.0/24에 매칭 → eth0으로 직접 전달
  │
  │  ④ ARP로 10.18.1.1의 MAC 주소 확인
  │  ─────────────────────────
  │  10.18.1.1은 kube-vip VIP → 현재 VIP를 보유한 마스터의 MAC 주소 응답
  │  (예: raspberrypi-0의 MAC)
  │
  │  ⑤ eth0에서 패킷 송출
  │
  ▼
LAN (이더넷 프레임)
  ┌─────────────────────────────────────────┐
  │ Ethernet Header                         │
  │   src MAC: Pi 5 SR의 eth0 MAC          │
  │   dst MAC: raspberrypi-0의 eth0 MAC    │
  │                                         │
  │ IP Header                               │
  │   src: 100.64.0.1 (MacBook)            │
  │   dst: 10.18.1.1  (kube-vip VIP)       │
  │                                         │
  │ TCP Header                              │
  │   dst_port: 6443                        │
  │ Payload: TLS ClientHello                │
  └─────────────────────────────────────────┘
```

**핵심**:
- Pi 5 SR이 하는 일은 **WireGuard 복호화 → IP 포워딩** 두 가지뿐
- SNAT이 비활성화되어 있으므로 소스 IP(100.64.0.1)가 그대로 유지됨
- LAN에 풀어놓는 패킷의 목적지는 kube-vip VIP(10.18.1.1)
- ARP 요청으로 VIP를 보유한 마스터의 MAC 주소를 알아내고, 해당 마스터에 직접 전달

## 6단계: kube-vip VIP → K8s API 서버

```
raspberrypi-0 (10.18.1.10, kube-vip VIP 10.18.1.1 보유 중)
  │
  │  ① 수신: dst=10.18.1.1:6443
  │  kube-vip가 VIP를 이 노드의 네트워크 인터페이스에 바인딩하고 있음
  │  → 커널이 이 패킷을 로컬 수신으로 판단
  │
  │  ② kube-apiserver가 6443 포트에서 수신 대기 중
  │  → TCP handshake → TLS handshake
  │  → kubectl 인증 (kubeconfig의 client certificate 검증)
  │  → "get nodes" 요청 처리
  │
  │  ③ 응답 생성
  │  ┌─────────────────────────────────────┐
  │  │ IP Header                           │
  │  │   src: 10.18.1.1  (VIP)            │
  │  │   dst: 100.64.0.1 (MacBook)        │
  │  │ TCP Header                          │
  │  │   src_port: 6443                    │
  │  │ Payload: JSON (node list)           │
  │  └─────────────────────────────────────┘
```

**핵심**: kube-apiserver는 Tailscale의 존재를 전혀 모른다. 일반적인 TCP 요청을 받고 응답할 뿐이다. 소스 IP가 100.64.0.1(Tailscale 대역)이지만, kube-apiserver는 이것이 어디서 온 것인지 신경 쓰지 않는다 (kubeconfig 인증서 기반 인증만 확인).

## 7단계: 응답 패킷의 귀환 경로

K8s API 서버의 응답이 다시 카페 노트북까지 돌아가는 과정.

```
raspberrypi-0 (10.18.1.10)
  │
  │  응답 패킷: src=10.18.1.1, dst=100.64.0.1
  │
  │  라우팅 테이블 조회:
  │  "100.64.0.1은 어디로?"
  │  → 일반 라우팅 테이블에 100.64.0.0/10 항목 없음
  │  → default gateway (공유기)로 전달
  │
  ▼
자택 공유기
  │
  │  "100.64.0.1? 모르는 주소 → ISP로?"
  │
  │  ✗ 여기서 막힘! ... 이 되어야 하지만, 실제로는:
  │
  │  Pi 5 SR이 SNAT=false이므로 소스 IP가 100.64.0.1
  │  → 이 경우 응답 경로 문제 발생 가능
```

### 실제 동작: Tailscale의 SNAT 처리

위의 문제를 해결하기 위해, SNAT 비활성화 시 Tailscale은 **Pi 5 SR 자체에서 역방향 라우팅을 처리**한다.

실제로는 두 가지 방식 중 하나로 동작한다:

#### 방식 A: SNAT 활성화 (기본값, `--snat-subnet-routes` 미지정 시)

```
Pi 5 SR → LAN으로 패킷을 보낼 때:
  원본 src: 100.64.0.1 (MacBook)
  변환 src: 10.18.1.50 (Pi 5 SR 자신의 LAN IP)

K8s 마스터가 보는 소스 IP: 10.18.1.50
  → 응답: dst=10.18.1.50 → 같은 LAN → Pi 5 SR에 직접 도달
  → Pi 5 SR: conntrack으로 원래 연결 추적 → WireGuard로 돌려보냄
```

이 경우 응답 경로 문제가 발생하지 않는다. K8s 마스터는 같은 LAN의 Pi 5 SR에게 응답을 보내면 된다.

#### 방식 B: SNAT 비활성화 (`--snat-subnet-routes=false`)

```
Pi 5 SR → LAN으로 패킷을 보낼 때:
  src: 100.64.0.1 (MacBook, 변환 없음)

K8s 마스터가 보는 소스 IP: 100.64.0.1
  → 응답: dst=100.64.0.1
  → 라우팅 테이블에 100.64.0.0 경로 없음
  → default gateway (공유기)로 전달
  → 공유기도 모름 → 패킷 유실 ✗
```

**이 문제를 해결하는 방법**: Pi 5 SR에 `--snat-subnet-routes=false`를 사용하면서 외부 → 자택 단방향 접근만 하는 경우, Tailscale은 내부적으로 **4-in-6 캡슐화** 또는 **policy routing**을 사용하여 응답 패킷이 Pi 5 SR로 돌아오도록 처리한다. 구체적으로:

```
Pi 5 SR의 처리:
  ① 외부 → LAN 패킷을 전달할 때, 커널의 conntrack 테이블에 연결 기록
  ② 실제로는 tailscale0 인터페이스에서 eth0으로의 포워딩 경로에
     iptables/nftables MASQUERADE 규칙이 자동 적용됨
  ③ 즉, --snat-subnet-routes=false는 "Tailscale IP 간 SNAT 비활성화"이며,
     100.64.x.x → 10.18.x.x 방향의 기본적인 masquerade는 유지됨

결과:
  K8s 마스터가 보는 src: 10.18.1.50 (Pi 5 SR)
  응답: dst=10.18.1.50 → LAN 직접 → Pi 5 SR → WireGuard → MacBook
```

**정리**: `--snat-subnet-routes=false`는 주로 **사이트 간 통신**(자택 SR ↔ AWS SR)에서 소스 IP를 투명하게 유지하기 위한 설정이다. 외부 Tailscale 클라이언트(100.64.x.x) → LAN 접근 시에는 Tailscale이 자동으로 적절한 NAT 처리를 수행한다.

## 레이턴시 분석

각 단계에서 추가되는 레이턴시.

| 단계 | 처리 | 예상 레이턴시 |
|------|------|--------------|
| [1]~[2] kubectl → tailscale0 | OS 라우팅 | < 0.1ms |
| [3] WireGuard 암호화 | ChaCha20-Poly1305 | < 0.5ms |
| [4]~[5] MacBook → 카페 공유기 | Wi-Fi + NAT | 1~5ms |
| [6] 인터넷 경유 | 물리적 거리 의존 | 5~50ms |
| [7] 자택 공유기 NAT | NAT 조회 | < 0.5ms |
| [8] WireGuard 복호화 | ChaCha20-Poly1305 (Pi 5 ARM crypto) | < 1ms |
| [9] IP 포워딩 + ARP | 커널 처리 | < 0.1ms |
| [10] API 서버 처리 | K8s 요청 처리 | 10~100ms |
| **합계 (편도)** | | **약 20~160ms** |

- 대부분의 레이턴시는 **[6] 인터넷 경유**와 **[10] API 서버 처리**에서 발생
- WireGuard 암호화/복호화 오버헤드는 무시할 수 있는 수준
- 직접 연결 대비 DERP 릴레이 경유 시 [6] 단계가 2배 정도 증가

## 자주 하는 오해

### "Pi 5 SR은 프록시인가?"

아니다. 프록시는 애플리케이션 레이어(L7)에서 요청을 중계하지만, Pi 5 SR은 네트워크 레이어(L3)에서 패킷을 포워딩한다. Pi 5 SR은 패킷의 내용(kubectl 요청인지, 웹 요청인지)을 전혀 모른다.

### "VPN이면 느리지 않나?"

사이트 **내** 통신은 VPN을 경유하지 않는다. K8s 노드 간 통신은 기존 LAN 직접 통신이므로 성능 영향이 전혀 없다. VPN 오버헤드는 외부 → 내부 접근(이 문서의 시나리오)에서만 발생하며, 이는 주로 kubectl 등의 관리 트래픽이므로 영향이 미미하다.

### "공유기에 포트포워딩이 필요한 것 아닌가?"

필요 없다. Pi 5 SR이 먼저 outbound UDP 연결을 맺고, 외부에서 오는 패킷은 이 연결의 응답으로 처리된다 (NAT traversal). 공유기는 "Pi 5가 인터넷으로 UDP를 주고받고 있다" 정도로만 인식한다.

### "K8s 노드에 Tailscale 관련 설정이 필요한가?"

전혀 필요 없다. K8s 노드는 Tailscale의 존재를 모른다. 외부에서 온 패킷은 Pi 5 SR이 복호화하여 일반 LAN 패킷으로 전달하므로, K8s 노드 입장에서는 LAN 내 다른 장치(Pi 5 SR)가 보낸 일반 패킷일 뿐이다.
