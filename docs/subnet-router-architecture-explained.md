# 기존 공유기 + Pi 5 Subnet Router 구조 설명

## 물리적 구성

```
인터넷
  │
  ▼
기존 공유기 (10.18.1.1 ← 이것은 공유기 IP가 아니라 kube-vip VIP)
  │  NAT, DHCP, DNS, 방화벽 — 기존과 동일
  │
  ├─── LAN ──────────────────────────────────────────┐
  │                                                    │
  │  ┌─────────────────────────────────────────────┐   │
  │  │ K8s 클러스터 (Tailscale 미설치)             │   │
  │  │  마스터: 10.18.1.10, .11, .12              │   │
  │  │  워커:   10.18.2.10, .11, 10.18.3.100     │   │
  │  └─────────────────────────────────────────────┘   │
  │                                                    │
  │  ┌──────────────────────────┐                      │
  │  │ Pi 5 (Tailscale SR 전용) │                      │
  │  │ IP: 10.18.1.50 (예시)    │                      │
  │  │ Tailscale 설치됨          │                      │
  │  │ 이더넷 포트 1개면 충분    │                      │
  │  └──────────────────────────┘                      │
  │                                                    │
  └────────────────────────────────────────────────────┘
```

**핵심**: Pi 5 SR은 그냥 LAN에 연결된 **평범한 장치 하나**. 공유기와 K8s 노드 사이에 끼어들지 않음.

## 왜 이더넷 포트 1개로 충분한가

Pi 5 SR은 공유기가 **아님**. 트래픽이 Pi 5를 "통과"하는 구조가 아님.

```
잘못된 이해 (공유기 역할):
  인터넷 → [Pi 5 WAN 포트] → [Pi 5 LAN 포트] → K8s 노드
  (포트 2개 필요)

올바른 이해 (SR 역할):
  Pi 5는 LAN에 그냥 붙어있고,
  Tailscale 터널의 출구 역할만 함
  (포트 1개로 충분)
```

## 동작 원리: 시나리오별 트래픽 흐름

### 시나리오 1: 자택 LAN 내 통신 (SR 무관)

```
K8s 마스터(10.18.1.10) ←──── LAN 직접 통신 ────→ K8s 워커(10.18.2.10)
```

- Pi 5 SR은 **관여하지 않음**
- 기존과 완전히 동일한 LAN 통신
- Pi 5가 꺼져 있어도 영향 없음

### 시나리오 2: 외부에서 K8s 클러스터 접근 (Tailscale 경유)

예: 카페에서 노트북으로 `kubectl get nodes` 실행

```
① 카페 노트북 (Tailscale 설치됨, 100.x.x.1)
   │
   │  "10.18.1.10에 접속하고 싶다"
   │
   ▼
② Tailscale 조정 서버 (coordination server)
   │
   │  "10.18.0.0/16은 Pi 5 SR이 광고 중 → Pi 5로 보내라"
   │
   ▼
③ WireGuard 암호화 터널 (인터넷 경유)
   │
   │  카페 노트북 ───── 암호화된 패킷 ─────→ Pi 5 SR
   │
   ▼
④ Pi 5 SR (10.18.1.50)
   │
   │  WireGuard 복호화 → 목적지 10.18.1.10 확인
   │  eth0 인터페이스로 LAN에 전달 (ip_forward=1)
   │
   ▼
⑤ K8s 마스터 (10.18.1.10)
   │
   │  응답 → Pi 5 SR → WireGuard 암호화 → 카페 노트북
```

**Pi 5 SR의 역할**: Tailscale 터널의 "출구". 외부에서 온 패킷을 복호화해서 LAN에 풀어놓고, 응답을 다시 암호화해서 돌려보냄.

### 시나리오 3: K8s 노드가 인터넷 접속 (SR 무관)

```
K8s 워커(10.18.2.10) ──→ 기존 공유기 (NAT) ──→ 인터넷
```

- 기존과 동일. Pi 5 SR은 **관여하지 않음**
- Docker 이미지 pull, apt update 등 모두 기존 경로

### 시나리오 4: 향후 AWS 워커 노드 추가 시

```
자택 LAN                              AWS VPC
┌──────────────────┐                  ┌──────────────────┐
│ K8s 마스터        │                  │ K8s 워커 (신규)  │
│ 10.18.1.10~12    │                  │ 10.0.1.x         │
│                  │                  │                  │
│ Pi 5 SR          │  WireGuard 터널  │ EC2 SR           │
│ 10.18.1.50       │◄════════════════►│ 10.0.1.y         │
│ 광고: 10.18.0/16 │                  │ 광고: 10.0.0/16  │
└──────────────────┘                  └──────────────────┘
```

- 양쪽에 SR이 하나씩 있으면 두 사이트가 마치 같은 네트워크처럼 통신
- K8s 노드에는 Tailscale 설치 불필요
- **주의**: 이 시나리오에서는 공유기에 정적 라우트 추가 필요 (아래 "공유기에 필요한 설정" 섹션 참조)

## 공유기에 필요한 설정

### 단일 사이트 (자택만, 외부에서 원격 접속)

| 질문 | 답변 |
|------|------|
| 공유기가 Tailscale 트래픽을 알아야 하나? | 아니오. Pi 5와 외부 간 WireGuard 트래픽은 일반 UDP로 보임 |
| 공유기에 포트포워딩이 필요한가? | 아니오. Tailscale은 **outbound** 연결을 사용 (NAT traversal) |
| 공유기에 라우팅 설정이 필요한가? | 아니오. Pi 5가 LAN 패킷을 직접 전달 |
| 공유기 DHCP/DNS 변경이 필요한가? | 아니오. Pi 5에 고정 IP 하나 할당하면 끝 |

Tailscale은 양쪽 모두 **outbound** UDP 연결을 맺고, STUN/DERP를 통해 NAT을 통과함. 공유기 입장에서는 Pi 5가 인터넷으로 UDP 패킷을 주고받는 것처럼 보일 뿐.

### 멀티사이트 (자택 + AWS): 정적 라우트 필요

자택 K8s 노드가 AWS 노드(10.0.x.x)로 패킷을 보내는 경우를 생각해 보자:

```
정적 라우트 없이:
  K8s 노드: "10.0.1.x는 내 LAN이 아니니까 → 기본 게이트웨이(공유기)로"
  공유기:    "10.0.1.x? 모르는 주소 → ISP(인터넷)로"
  결과:      패킷 유실 ✗

정적 라우트 추가 후:
  K8s 노드: "10.0.1.x → 기본 게이트웨이(공유기)로"
  공유기:    "10.0.0.0/16 → 10.18.1.50(Pi 5 SR)으로" ← 정적 라우트
  Pi 5 SR:  WireGuard 암호화 → Tailscale 터널 → AWS
  결과:      정상 도달 ✓
```

공유기에 추가할 정적 라우트:

```
목적지: 10.0.0.0/16  →  게이트웨이: 10.18.1.50 (Pi 5 SR)
```

이 설정이 필요한 이유: K8s 노드는 Tailscale을 모르므로, AWS 대역 트래픽을 공유기(기본 게이트웨이)로 보낸다. 공유기가 이 트래픽을 Pi 5 SR로 전달해야 Tailscale 터널을 통해 AWS에 도달한다.

### 공유기 설정 요약

| 설정 | 용도 | 필요 시점 |
|------|------|-----------|
| (없음) | 단일 사이트 원격 접속 | Phase 1 |
| 정적 라우트 10.0.0.0/16 → Pi 5 SR | AWS ↔ 자택 양방향 통신 | Phase 2 (AWS 사이트 추가 시) |
| 포트포워딩 80/443 → LB IP | Public endpoint 노출 | Ingress 구축 시 (Tailscale과 무관) |

## Pi 5 SR이 고장나면?

| 기능 | 영향 |
|------|------|
| 자택 인터넷 | **정상** (공유기가 처리) |
| LAN 내 K8s 통신 | **정상** (직접 통신) |
| 외부 → K8s 원격 접속 | **불가** (터널 끊김) |

기존 공유기를 교체하는 방식이었다면 Pi 5 고장 = 인터넷 전체 다운. SR 전용 방식은 원격 접속만 불가.

## Pi 5 SR에 필요한 설정 (전부)

```bash
# 1. Tailscale 설치
curl -fsSL https://tailscale.com/install.sh | sh

# 2. 커널 파라미터 (패킷 포워딩 활성화)
cat > /etc/sysctl.d/99-tailscale.conf << 'EOF'
net.ipv4.ip_forward = 1
net.ipv4.conf.all.rp_filter = 2
net.ipv4.conf.default.rp_filter = 2
EOF
sysctl --system

# 3. Subnet Router로 실행
tailscale up --advertise-routes=10.18.0.0/16 --snat-subnet-routes=false --accept-routes

# 4. Tailscale Admin Console에서 route 승인 (또는 ACL autoApprovers 설정)
```

이것이 전부. NAT, DHCP, DNS, 방화벽 설정 없음.

## Public Endpoint 노출과의 관계

Tailscale SR과 public endpoint 노출(Ingress + cert-manager)은 **별개의 문제**:

| 목적 | 해결 수단 | 공유기 설정 |
|------|-----------|-------------|
| 외부에서 K8s 관리 (kubectl 등) | Tailscale SR | 단일 사이트: 불필요 / 멀티사이트: 정적 라우트 |
| 인터넷에 웹 서비스 공개 | 포트포워딩 + Ingress | 80/443 포트포워딩 필요 |

포트포워딩은 Tailscale과 무관하게 공유기에서 설정해야 하는 부분.
